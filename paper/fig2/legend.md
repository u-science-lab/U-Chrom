**Figure 2 — One ChromData store holds more kinds of chromatin data than existing containers, and serves them at real scale.** **a**, The ChromData data model: `spots` (one row per observation) point at a shared locus axis (`bins`) through `bin_id`, and at `traces` and `cells` through `trace_id` and `cell_id`; coordinates (+ layers) and per-spot tracks are row-aligned with the spots, contact maps are linked by bins and a cell map rather than copied. Right: the `x.chromdata.zarr` layout (format 2.3) as written by `uchrom.core.zarrcd`; the glyph at each node gives its storage type (Parquet table, Zarr array, JSON attributes). Every spot-aligned value is stored once: coordinates and keys in one Parquet table per chromosome, every other spot-aligned column in cell-sorted primary tables, and spot columns that only repeat a value of their bin, cell or trace once per key; `index/` maps the (cell, trace, chromosome) runs of the two sides one to one. **b**, What each format can represent: chromdata.zarr, the 4DN FOF-CT tables (v1.0), AnnData (0.12.11), SpatialData (0.7.2), MuData (0.3.4) and cooler (.cool / .scool, 0.10.4). Columns (full definitions in Supplementary Table S1): spot coordinates (x, y, z), the position of every spot (one imaged or reconstructed locus in one trace) with its unit; cell › trace › spot, which trace and which cell each spot belongs to, as nested levels; per-spot signals, values measured at each spot (e.g. immunofluorescence); per-locus signals, values per genomic bin shared by all cells (e.g. bulk ATAC); cell table, scalar properties per cell; cell embeddings, a multi-dimensional vector per cell; cell spatial position, each cell's centroid and / or outline in the tissue or field of view, with unit and frame; contact maps, locus × locus contact counts; intervals, TADs and loops called on the data; RNA spots (points), 3-D points that are not genomic loci; results + provenance, analysis results stored as data with the function, parameters and version that produced them; partial reads, one cell's or one chromosome's rows read from disk without reading the rest. Filled, native (first-class, with its own structure); teal ring, linked (kept in an external community-standard file, not copied, and queried through the shared index — how chromdata.zarr holds contact maps: .cool / .scool); open, by convention (stored and read back through the library's API only in a general-purpose slot such as `uns`, `obsm`, `varp`, `attrs`, metadata attributes or extra / optional columns, so the structure is lost or ad hoc; it must be a normal use of the format, not merely an encoding that writes); dash, not supported. AnnData and MuData are rated in their most favourable orientation (spots, cells or loci as observations), and these orientations exclude each other in one object (one AnnData, one MuData modality). Every library mark was checked by a small test that stores the element with that library's own API, writes it, reads it back and records which kind of slot held it; a test that needed a general-purpose slot can back at most 'by convention' (`benchmarks/fig2/b_capabilities.py`; FOF-CT from its specification pages). The evidence decides; only genuinely ambiguous cells give the other tool the better mark (flagged as judgement calls in Table S1). A data table serialised to JSON text in a metadata attribute does not count; a cell's own properties in the metadata of its cooler in a .scool do, as a general-purpose slot. Partial reads are native when one cell's or one chromosome's rows are read from disk without reading the other rows (beyond the selection key), and by convention when this needs a scan of every row or loads part of the data whole (MuData backed mode loads `obs` / `obsm`). Evidence per cell, with documentation links, versions and the changes made in the audits, is in Supplementary Table S1; which fields survive an export → import round trip is in Supplementary Fig. S1e. **c**, File size and full-read time (into memory) vs number of spots for whole-cell subsets of the Takei et al. 2025 cerebellum DNA seqFISH+ data (62 per-spot tracks), for chromdata.zarr 2.2 and the storage schemes publicly used by the community for chromatin-tracing data — the 4DN FOF-CT core table (CSV, official `uchrom.io.write_fofct` / `ChromData.from_fofct`), AnnData with spots as observations (`write_h5ad` / `read_h5ad`) and SpatialData (spots as a 3-D points element, cells as a table; `spatialdata` 0.7.2 defaults, full read = `read_zarr` + `.compute()`); median of 3 fresh processes. At 1e7 spots chromdata.zarr stores 1.8 GB and reads in 0.57 s (FOF-CT 6.7 GB, 99 s; AnnData 5.6 GB, 5.4 s; SpatialData 2.2 GB, 2.2 s). Flat Parquet (the storage engine under chromdata.zarr) and the ChromData format versions are in Supplementary Fig. S1a,b. **d**, Access from disk (median of 20 random ids × 3 fresh processes; shading, IQR). Left, access by level in backed chromdata.zarr (`ChromData.read(path, backed=True)`): `get_trace`, `get_cell`, `get_chrom` with coordinates only, and opening the store; at 1e7 spots 6.2 ms, 9.0 ms, 13 ms and 36 ms, at 1e8 16 ms, 26 ms, 0.14 s and 0.20 s.
