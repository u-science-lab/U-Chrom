**Figure 2 — One ChromData store holds more kinds of chromatin data than existing containers, and serves them at real scale.** **a**, The ChromData data model: `spots` (one row per observation) point at a shared locus axis (`bins`) through `bin_id`, and at `traces` and `cells` through `trace_id` and `cell_id`; coordinates (+ layers) and per-spot tracks are row-aligned with the spots, contact maps are linked by bins and a cell map rather than copied. Right: the `x.chromdata.zarr` layout (format 2.2) as written by `uchrom.core.zarrcd`; the glyph at each node gives its storage type (Parquet table, Zarr array, JSON attributes). Every spot-aligned value is stored once: coordinates and keys in one Parquet table per chromosome, every other spot-aligned column in cell-sorted primary tables, and spot columns that only repeat a value of their bin, cell or trace once per key; `index/` maps the (cell, trace, chromosome) runs of the two sides one to one. **b**, What each format can represent: chromdata.zarr, the 4DN FOF-CT tables (v1.0), AnnData (0.12.11), SpatialData (0.7.2), MuData (0.3.4) and cooler (.cool / .scool, 0.10.4) against ten chromatin data elements. Filled, native (first-class, with its own structure); teal ring, linked (kept in an external community-standard file, not copied, and queried through the shared index — how chromdata.zarr holds contact maps: .cool / .scool); open, by convention (stored and read back through the library's API in a general-purpose slot such as `uns`, `obsm` or extra columns, so the structure is lost or ad hoc); dash, not supported. Every library mark was checked by a small test that stores the element with that library's own API and reads it back (`benchmarks/fig2/b_capabilities.py`; FOF-CT from its specification). Where in doubt the other tool got the better mark; AnnData elements are rated in their most favourable orientation (spots, cells or loci as observations), which exclude each other in one object; AnnData, SpatialData and MuData have no contact-map type (one locus × locus matrix can be placed in varp), so they are marked by convention. Evidence per cell, with documentation links and versions, is in Supplementary Table S1; which fields survive an export → import round trip is in Supplementary Fig. S1e. **c**, File size and full-read time (into memory) vs number of spots for whole-cell subsets of the Takei et al. 2025 cerebellum DNA seqFISH+ data (62 per-spot tracks), for chromdata.zarr 2.2 and the storage schemes publicly used by the community for chromatin-tracing data — the 4DN FOF-CT core table (CSV, official `uchrom.io.write_fofct` / `ChromData.from_fofct`), AnnData with spots as observations (`write_h5ad` / `read_h5ad`) and SpatialData (spots as a 3-D points element, cells as a table; `spatialdata` 0.7.2 defaults, full read = `read_zarr` + `.compute()`); median of 3 fresh processes. At 1e7 spots chromdata.zarr stores 1.8 GB and reads in 0.57 s (FOF-CT 6.7 GB, 99 s; AnnData 5.6 GB, 5.4 s; SpatialData 2.2 GB, 2.2 s). Flat Parquet (the storage engine under chromdata.zarr) and the ChromData format versions are in Supplementary Fig. S1a,b. **d**, Access from disk (median of 20 random ids × 3 fresh processes; shading, IQR). Left, access by level in backed chromdata.zarr (`ChromData.read(path, backed=True)`): `get_trace`, `get_cell`, `get_chrom` with coordinates only, and opening the store; at 1e7 spots 6.2 ms, 9.0 ms, 13 ms and 36 ms, at 1e8 16 ms, 26 ms, 0.14 s and 0.20 s. Right, the time to get one cell's data from the file, for each format: chromdata.zarr, open + backed `get_cell` (45 ms at 1e7 spots); AnnData, load the `.h5ad` + subset (7.6 s); SpatialData, lazy open + a dask filter on `cell_id` + `.compute()` (0.75 s); FOF-CT, load the CSV + subset (8.4 s at 1e6). FOF-CT stops at 1e6 spots because loading the 1e7-spot CSV exceeds our 40 GB peak-memory safety limit. `get_chrom` with all 62 tracks (0.52 s at 1e7: it reads a slice of every cell-sorted row group), the layouts 2.0 / 2.1 and the per-format `get_trace` / `get_chrom` are in Supplementary Fig. S1c,d,f,g. **e**, Beyond RAM. Left: memory used to open the data and answer the trace and cell queries of **d** (above the interpreter's baseline), backed chromdata.zarr vs the whole table loaded (colours as in **d**).
