# Supplementary Table S1 — What each format can represent (evidence for Fig. 2b)

Generated by `benchmarks/fig2/b_capabilities.py` from `paper/fig2/results/b_capabilities.json`; do not edit by hand.

**Marks.** ● *native*: first-class, with its own structure. ○ *by convention*: stored and read back through the library's public API, but only in a general-purpose slot (`uns`, `obsm`, extra columns, attributes), so the structure is lost or ad hoc. – *not supported*: no place for it in the format or its API.

**Rules (fair and conservative toward the other tools).** (1) If in doubt, the other tool gets the better mark, and the note says so. (2) AnnData has a single observation axis: each element is rated in its most favourable orientation (spots, cells or loci as `obs` / `var`), although these orientations exclude each other in one object; the hierarchy column is where that shows. (3) A data table serialised to JSON text inside a descriptive metadata attribute (cooler's `metadata`) does not count; such tests are still run and reported as *not counted*. Provenance-like metadata there does count.

**Tests.** ✓ = a tiny test in `benchmarks/fig2/b_capabilities.py` stored the element with that library's own API, wrote it to disk, read it back and compared the values; FOF-CT is a CSV specification, not a library, so its row rests on the specification pages alone.

**Versions checked.** uchrom 0.2.0; anndata 0.12.11; spatialdata 0.7.2; mudata 0.3.4; cooler 0.10.4; zarr 3.1.6; h5py 3.16.0; FOF-CT v1.0 (specification pages checked 2026-09-26).
