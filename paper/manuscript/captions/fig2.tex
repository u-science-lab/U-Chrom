\textbf{One ChromData store holds more kinds of chromatin data than existing containers, and serves them at real scale.}
\textbf{a}~The ChromData data model: \pkg{spots} (one row per observation) point at a shared locus axis (\pkg{bins}) through \pkg{bin\_id}, and at \pkg{traces} and \pkg{cells} through \pkg{trace\_id} and \pkg{cell\_id}; coordinates (+ layers) and per-spot tracks are row-aligned with the spots, and contact maps are linked by bins and a cell map rather than copied.
Right: the \pkg{x.chromdata.zarr} layout (format 2.3) as written by \pkg{uchrom.core.zarrcd}; the glyph at each node gives its storage type (Parquet table, Zarr array, JSON attributes).
Every spot-aligned value is stored once: coordinates and keys in one Parquet table per chromosome, every other spot-aligned column in cell-sorted primary tables, and spot columns that only repeat a value of their bin, cell or trace once per key; \pkg{index/} maps the (cell, trace, chromosome) runs of the two sides one to one.
\textbf{b}~What each format can represent: chromdata.zarr, the 4DN FOF-CT tables (v1.0), AnnData (0.12.11), SpatialData (0.7.2), MuData (0.3.4) and cooler (.cool / .scool, 0.10.4).
Columns (full definitions in Supplementary Table~S1): spot coordinates (x, y, z), the position of every spot (one imaged or reconstructed locus in one trace) with its unit; cell › trace › spot, which trace and which cell each spot belongs to, as nested levels; per-spot signals, values measured at each spot (e.g. immunofluorescence); per-locus signals, values per genomic bin shared by all cells (e.g. bulk ATAC); cell table, scalar properties per cell; cell embeddings, a multi-dimensional vector per cell; cell spatial position, each cell's centroid and / or outline in the tissue or field of view, with unit and frame; contact maps, locus × locus contact counts; intervals, TADs and loops called on the data; RNA spots (points), 3-D points that are not genomic loci; results + provenance, analysis results stored as data with the function, parameters and version that produced them; partial reads, one cell's or one chromosome's rows read from disk without reading the rest.
Filled, native (first-class, with its own structure); teal ring, linked (kept in an external community-standard file, not copied, and queried through the shared index --- how chromdata.zarr holds contact maps: .cool / .scool); open, by convention (stored and read back through the library's API only in a general-purpose slot such as \pkg{uns}, \pkg{obsm}, \pkg{varp}, \pkg{attrs}, metadata attributes or extra / optional columns, so the structure is lost or ad hoc; it must be a normal use of the format, not merely an encoding that writes); dash, not supported.
AnnData and MuData are rated in their most favourable orientation (spots, cells or loci as observations), and these orientations exclude each other in one object (one AnnData, one MuData modality).
Every library mark was checked by a small test that stores the element with that library's own API, writes it, reads it back and records which kind of slot held it; a test that needed a general-purpose slot can back at most `by convention' (FOF-CT from its specification pages).
The evidence decides; only genuinely ambiguous cells give the other tool the better mark (flagged as judgement calls in Table~S1).
A data table serialised to JSON text in a metadata attribute does not count; a cell's own properties in the metadata of its cooler in a .scool do, as a general-purpose slot.
Partial reads are native when one cell's or one chromosome's rows are read from disk without reading the other rows (beyond the selection key), and by convention when this needs a scan of every row or loads part of the data whole (MuData backed mode loads \pkg{obs} / \pkg{obsm}).
Evidence per cell, with documentation links, versions and the changes made in the audits, is in Supplementary Table~S1.
