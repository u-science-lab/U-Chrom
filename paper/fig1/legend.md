**Fig. 1 — U-Chrom places sequencing- and imaging-based 3-D genome data on one shared index.** **a** Each assay captures one facet of 3-D genome organisation: contacts (Hi-C, scHi-C; which loci touch), geometry (chromatin tracing; where loci are) and molecular state (ChIP, ATAC, RNA, immunofluorescence (IF); what loci carry). Left wall, scHiCAR contact map of mouse primary motor cortex (5,313 cells merged; chr7:53–68 Mb; 250-kb bins; ICE-balanced). Floor, H3K27ac, LaminB1 and H3K9me3 IF along chr15 in one cerebellar cell (DNA seqFISH+; 48 bins). **b** ChromData is a shared index, not a joint model. Each modality is its own layer: geometry (x, y, z), contacts (bin × bin maps, linked when large) and molecular features; the same genomic bins index every layer (dashed lines). Left, any layer can be held at the population, cell or trace › spot level; aggregation moves data up a level (deconvolution is planned). Right, operations within and between layers: imputation, reconstruction from contacts, and conversion of distances into contact frequencies; molecular features are projected onto structures through a shared spot, cell or cell type. Plate contents are schematic, derived from the data in **a**. **c** The U-Chrom ecosystem. Community formats are read, or linked without copying (dashed boxes); ChromData is stored as a .chromdata.zarr store (Zarr with Parquet tables; .cdz, the same store in one zip file); structures are exported as PDB. Five analysis modules (reconstruction, imaging-side processing, structure calling, geometric features, cell embeddings) share one API, reached from Python, a command-line interface, a web browser and a Model Context Protocol (MCP) server.
